# 概要

このファイルはリポジトリ内のGitブランチ運用ルールをまとめたドキュメントです。

# ブランチ運用戦略について

Gitのブランチ運用戦略にはいくつかの代表的なモデルが存在する。   
それぞれの特徴と適したユースケースをまとめてみた。

## 1. Git Flow

最も古典的で体系的なモデル。

**ブランチ構成:**

- `main`(または`master`) — 本番リリース用
- `develop` — 開発の統合ブランチ
- `feature/*` — 機能開発用(developから分岐・マージ)
- `release/*` — リリース準備用
- `hotfix/*` — 本番の緊急修正用

**特徴:**

- 明確なルールがあり、大規模チームや厳格なリリース管理に向く
- ブランチ数が多く、運用がやや複雑
- リリースサイクルが長い(週次・月次など)プロダクトに適している
- 現在はCI/CD時代にはやや重厚と見なされることも多い

## 2. GitHub Flow

シンプルさを重視したモデルです。

**ブランチ構成:**

- `main` — 常にデプロイ可能な状態を保つ
- `feature/*` — mainから分岐し、Pull Requestでmainにマージ

**特徴:**

- ブランチが少なくシンプル
- 継続的デプロイ(CD)と相性が良い
- リリースするプロダクトに向く
- リリースバージョン管理が弱い(複数バージョンを並行運用するのは苦手)

## 3. GitLab Flow

Git FlowとGitHub Flowの中間的なアプローチです。

**特徴:**

- `main`に加えて環境ごとのブランチ(`staging`, `production`など)を持つパターン
- または`main`とリリースブランチを組み合わせるパターンもある
- 環境ごとのデプロイフローを表現しやすい

## 4. Trunk-Based Development(トランクベース開発)

近年のCI/CDやDevOpsの潮流で注目されているモデルです。

**特徴:**

- 単一の`main`(トランク)ブランチに全員が頻繁に(1日に何度も)コミット
- 機能開発が長期化する場合はFeature Flag(機能フラグ)で未完成機能を隠す
- 短命なブランチ(数時間〜1日程度)のみ許容
- 大規模チーム・高頻度デプロイの現場(Google、Facebookなど)で採用例が多い
- マージコンフリクトが起きにくく、CI/CDと親和性が高い

## 選定のポイント

| 観点        | Git Flow | GitHub Flow | Trunk-Based |
|-----------|----------|-------------|-------------|
| リリース頻度    | 低〜中      | 高           | 非常に高        |
| チーム規模     | 中〜大      | 小〜中         | 中〜大         |
| 複数バージョン管理 | 得意       | 不得意         | 不得意         |

## 実務での判断基準

- **モバイルアプリやパッケージソフト**(複数バージョンを同時サポートする必要がある)→ Git Flowが向く
- **SaaS・Webサービス**(常に最新版のみ運用)→ GitHub FlowやTrunk-Basedが向く
- **チームの成熟度が低い・自動テストが未整備**→ まずはGitHub Flowのようなシンプルなモデルから始めるのが安全
- **デプロイ頻度が非常に高い(1日複数回)**→ Trunk-Based Development + Feature Flagが最適

# マージ方法について

Pull Requestをマージする際の3つのオプションについて、それぞれの動作と使い分けを記載。

## 1. Create a merge commit(マージコミット作成)

**動作:**

- feature branchの全コミット履歴をそのまま残し、マージコミットを1つ追加してmainに統合
- 履歴が分岐・合流するグラフ構造になる

```
main:    A---B-------M
              \     /
feature:       C---D
```

**メリット:**

- 完全な履歴が残る(いつ・どのブランチがマージされたか追跡しやすい)
- 元のコミットのハッシュが変わらない

**デメリット:**

- コミット履歴が複雑になりやすい(特にブランチが多いと`git log`が見づらい)
- 意味の薄い"WIP"や"fix typo"のようなコミットもそのまま残る

**向いているケース:**

- Git Flowのようにブランチ構造そのものに意味を持たせたい場合
- 誰が・いつ・どの単位で作業したかの追跡性を重視する場合

## 2. Squash and merge(スカッシュマージ)

**動作:**

- feature branchの全コミットを1つのコミットにまとめてmainに追加
- ブランチの分岐構造は残らない

```
main:    A---B---S(squashed)
```

**メリット:**

- mainの履歴が常に直線的でクリーン
- 1 PR = 1コミットとなり、`git log`が読みやすい
- 問題があった際の`git revert`が簡単(PR単位で取り消せる)

**デメリット:**

- feature branch内の個々のコミット履歴(試行錯誤の過程)は失われる
- 大きすぎるPRをスカッシュすると1コミットの差分が巨大になる

**向いているケース:**

- GitHub Flowなどシンプルな運用で、mainの履歴を綺麗に保ちたい場合
- 個人の作業スタイル(こまめなコミット)を気にせず自由にコミットしたい場合
- 現在最も一般的に採用されている方式(特にWebサービス開発)

## 3. Rebase and merge(リベースマージ)

**動作:**

- feature branchの各コミットを、mainの最新コミットの後ろに1つずつ付け替える
- マージコミットは作られず、履歴が直線になる(squashと違い個々のコミットは保持)

```
main:    A---B---C---D
                (元feature branchのコミットC,Dがそのまま並ぶ)
```

**メリット:**

- 履歴が直線的でクリーン、かつ個々のコミット単位の粒度も保持される
- マージコミットのノイズがない

**デメリット:**

- 元のコミットハッシュが変わる(リベースのため)
- コミット履歴が汚い(細かすぎる・意味不明な粒度)場合、そのままmainに残ってしまう
- 共有ブランチに対するリベースはコンフリクト解消が複雑になることがある

**向いているケース:**

- feature branch内のコミットがすでに整理されている(意味のある単位に分かれている)場合
- 直線的な履歴を保ちつつ、コミット粒度の情報も残したい場合

## 比較表

| 観点              | Merge commit | Squash and merge     | Rebase and merge |
|-----------------|--------------|----------------------|------------------|
| main履歴の形        | 分岐あり         | 直線                   | 直線               |
| featureの個々のコミット | 残る           | 消える(1つに統合)           | 残る               |
| revertのしやすさ     | やや複雑         | 簡単(PR単位)             | やや複雑             |
| コミットハッシュ        | 不変           | 変わる                  | 変わる              |
| 向いている運用         | Git Flow     | GitHub Flow / シンプル運用 | 整理されたコミット文化      |

## 実務での選び方の目安

- **チームのコミット文化が雑(WIP連発など)** → **Squash and merge**が無難(mainがクリーンに保たれる)
- **コミット単位でこまめにレビュー・追跡したい** → **Rebase and merge**(
  ただしチームがコミットを綺麗に整理する規律を持っている前提)
- **ブランチ単位の履歴・監査証跡を残したい**(大規模チーム、コンプライアンス要件がある) → **Create a merge commit**

多くのモダンなチーム(特にGitHub Flow採用チーム)では、運用のシンプルさから**Squash and merge をデフォルトにしつつ、必要に応じて他を許可する
**という設定がよく使われています。

# 運用ルール

2026年9月現在では、GitHub flowを採用します。
利用としては、CI/CDの整備がまだできておらず、開発メンバーも少なく、リリースができていないため   
シンプルな運用が現時点では適していると判断しました。

※mainブランチは常にリリース可能な状態を保つことを目的としていて直接PUSHできないようにブロックされています。

機能を開発する際は、mainからfeatureブランチを切り開発が完了したらPull
Requestを作成し、レビューを経てmainにマージする運用とします。    
(例：`feature/feature-name/main -> Pull Request -> main`)

またマージの際は、Create a merge commitを基本とし、必要に応じてSquash and mergeを許可する運用とします。
